# Диагностика: Fullstack TypeScript (NestJS + React + PostgreSQL), Middle

Банк вопросов для входной диагностики. Области и их ID совпадают с `CONCEPT-MAP.md`.

## Инструкция для тьютора

- **Формат:** вопросы задаются по одному, ответ свободный (устно или текстом), ответ даётся по памяти без поиска и IDE. На вопрос 1–3 минуты. Вариантов ответа нет. Если ученик просит подсказку, это фиксируется, и оценка становится не выше 1.
- **Бюджет:** не больше ~20 вопросов. В каждой области начинать с **уровня 2** (это 14 вопросов). Оставшиеся ~6 вопросов уходят на уточнения:
  - уровень 2 = 2 → задать уровень 3 (в первую очередь там, где L3 — кандидат в цель);
  - уровень 2 = 0 → задать уровень 1, чтобы отличить «не знает основ» от «знает, но не применял»;
  - уровень 2 = 1 → уточнение необязательно; по возможности уровень 3, если ответ был близок к 2.
- **Порядок областей:** сначала слабые места по самооценке, чтобы проверить их, пока хватает внимания: `react` → `pg` → `orm` → `be-test` → `fe-test`. Затем `nest` → `auth` → `fe-data` → `runtime` → `ts` → `http` → `perf` → `delivery` → `sysdesign`.
- **Оценка:** 0/1/2 по рубрике. Для «2» нужны **все** пункты из списка «Для 2 обязательно». Пункты «Бонус» на оценку не влияют, но говорят в пользу L3.
- **Перевод в глубину области:**

| Ответы | Фиксируемая глубина |
|---|---|
| ур.2 = 0, ур.1 = 0 или не задан | ниже `recall` |
| ур.2 = 0, ур.1 = 1–2 | `recall` / `explain` |
| ур.2 = 1 | `apply` частично |
| ур.2 = 2, ур.3 не задан или 0 | `apply` |
| ур.2 = 2, ур.3 = 1 | `apply`, `debug`/`design` частично |
| ур.2 = 2, ур.3 = 2 | `debug` / `design` |

- **Transferable:** такие вопросы проверяют навык, полезный за пределами конкретной технологии (рассуждение о конкурентности, о границах доверия, об отказах, о контрактах). Сильный ответ на них говорит о будущей скорости обучения больше, чем знание API.

## 1. `ts`: TypeScript

### ts.1 (recall)
**Вопрос:** Чем отличаются `any`, `unknown` и `never`? Приведите по одному примеру, где каждый уместен в прикладном коде.

**Рубрика:**
- **2.** Для 2 обязательно: (а) `any` отключает проверку типов: присваивается куда угодно и из чего угодно; (б) `unknown` принимает любое значение, но использовать его можно только после сужения (typeof, type guard, валидация); (в) `never` — тип без значений: результат исчерпывающего сужения, функции, которые бросают исключение или не завершаются; (г) уместные примеры: `unknown` для `JSON.parse`/`catch (e)`/внешних данных, `never` для exhaustive check в `switch`.
- **1.** Верно описаны два типа из трёх или нет примеров применения.
- **0.** Путает `unknown` с `any` или не знает `never`.

### ts.2 (apply)
**Вопрос:** Напишите сигнатуру (и, если успеете, тело) функции `pick`, чтобы:
```ts
const user = { id: 'u1', email: 'a@b.c', passwordHash: 'x', age: 30 };
const dto = pick(user, ['id', 'email']);
// typeof dto -> { id: string; email: string }
pick(user, ['id', 'phone']); // must be a compile error
```

**Рубрика:**
- **2.** Для 2 обязательно: (а) два параметра типа: `T` и `K extends keyof T`; (б) параметр `keys: K[]` (или `readonly K[]`); (в) возвращаемый тип `Pick<T, K>` (или эквивалентный mapped type `{ [P in K]: T[P] }`); (г) объяснение, почему `'phone'` не скомпилируется (ограничение `keyof T`) и как `K` выводится в объединение литералов `'id' | 'email'`. Пример: `function pick<T extends object, K extends keyof T>(obj: T, keys: readonly K[]): Pick<T, K>`.
- **1.** Generic есть, но результат `Partial<T>`/`any`/`Record<string, unknown>`, или нет ограничения `K extends keyof T`.
- **0.** Без generics или с `any`.
- **Бонус:** в теле нужен каст (`{} as Pick<T, K>`), и ученик объясняет, почему; упоминает `Omit` для обратной задачи (убрать `passwordHash`).

### ts.3 (debug/design) [Transferable: граница доверия]
**Вопрос:** Код компилируется без ошибок. Почему типы здесь не гарантируют корректность во время выполнения и как бы вы это исправили?
```ts
type ApiResponse<T> = { ok: true; data: T } | { ok: false; error: string };

async function getUser(id: string): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  const json = (await res.json()) as ApiResponse<User>;
  if (json.ok) return json.data;
  throw new Error(json.error);
}
```

**Рубрика:**
- **2.** Для 2 обязательно: (а) `as` — утверждение компилятору, а не проверка: в рантайме форма данных может быть любой (500 с HTML, другая версия API, `null`); (б) не проверяется `res.ok`/статус, а `res.json()` может бросить на не-JSON; (в) исправление через runtime-валидацию на границе: схема (zod/valibot) и `safeParse`, либо пользовательский type guard `(x: unknown): x is ApiResponse<User>`; (г) тип выводится из схемы (`z.infer`), чтобы не было двух источников истины.
- **1.** Понимает, что `as` небезопасен, но не предлагает конкретного механизма проверки, или предлагает только «проверить `res.ok`».
- **0.** Считает, что раз типы есть, всё безопасно.
- **Бонус:** общий пакет схем для фронта и бэка или генерация клиента из OpenAPI.

## 2. `runtime`: JavaScript и Node.js

### runtime.1 (recall)
**Вопрос:** Что такое event loop в Node.js? Что произойдёт с сервером, если внутри обработчика одного запроса синхронно выполнить тяжёлый цикл на 2 секунды?

**Рубрика:**
- **2.** Для 2 обязательно: (а) JS-код выполняется в одном потоке, event loop берёт колбэки из очередей (таймеры, I/O, `setImmediate`, микрозадачи), а I/O выполняется асинхронно средствами ОС и libuv (thread pool для fs/crypto/dns); (б) синхронный цикл блокирует обработку **всех** запросов на 2 с: растёт latency у всех клиентов, могут упасть health checks; (в) решение: вынести CPU-работу в `worker_threads`/отдельный процесс/очередь или разбить на части.
- **1.** Знает, что блокирует, но механизм описывает смутно, или описывает loop без последствий для сервера.
- **0.** Думает, что Node обработает другие запросы параллельно в других потоках.

### runtime.2 (apply) [Transferable: модель асинхронности]
**Вопрос:** Файл `main.cjs` (CommonJS) запускают через `node main.cjs`. Что выведется и почему?
```js
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
process.nextTick(() => console.log('4'));
(async () => {
  console.log('5');
  await null;
  console.log('6');
})();
console.log('7');
```

**Ключ:** `1 5 7 4 3 6 2` (проверено на Node 25).

**Рубрика:**
- **2.** Для 2 обязательно: (а) точный порядок `1 5 7 4 3 6 2`; (б) тело async-функции до первого `await` выполняется синхронно (поэтому `5` перед `7`); (в) после синхронного кода сначала очередь `process.nextTick`, затем микрозадачи промисов в порядке постановки (`3`, затем продолжение после `await` — `6`); (г) `setTimeout` — макрозадача, она выполняется после всех микрозадач.
- **1.** Синхронная часть и `2` в конце верны, но перепутан порядок `4`/`3`/`6` или нет объяснения.
- **0.** Ошибки в синхронной части (например, `5` после `7`) или `2` раньше микрозадач.
- **Бонус:** знает, что в ESM-модуле порядок будет `1 5 7 3 6 4 2`, потому что модуль исполняется внутри асинхронной задачи.

### runtime.3 (debug) [Transferable: управление конкурентностью]
**Вопрос:** Эндпоинт иногда отдаёт пустой массив, а при нагрузке база начинает отвечать ошибками «too many connections» и таймаутами. Найдите проблемы и предложите исправление.
```ts
app.get('/report', async (req, res) => {
  const ids = await getIds(); // ~10 000 ids
  const rows: Row[] = [];
  ids.forEach(async (id) => {
    rows.push(await db.getRow(id));
  });
  res.json(rows);
});
```

**Рубрика:**
- **2.** Для 2 обязательно: (а) `forEach` не ждёт async-колбэков, поэтому `res.json` отправляет пустой или частичный массив, а ошибки внутри уходят в unhandled rejection; (б) при этом 10 000 запросов стартуют одновременно и исчерпывают пул соединений; (в) замена на `Promise.all` без ограничения не решает (б), поэтому нужен один запрос `WHERE id = ANY($1)`/`IN (...)` (это по сути N+1) либо ограниченная конкурентность (батчи, p-limit); (г) для очень больших объёмов — пагинация или стриминг ответа.
- **1.** Находит проблему с `forEach` и предлагает `Promise.all`/`for...of`, но не видит проблемы 10 000 параллельных запросов или N+1.
- **0.** Не находит проблему с `forEach`.

## 3. `http`: HTTP и REST API

### http.1 (recall)
**Вопрос:** Что значит «идемпотентный метод»? Какие из GET, POST, PUT, PATCH, DELETE идемпотентны и почему это важно клиенту?

**Рубрика:**
- **2.** Для 2 обязательно: (а) определение: повтор одного и того же запроса N раз даёт то же состояние сервера, что и один раз (ответ может отличаться); (б) GET, PUT, DELETE идемпотентны, POST нет, PATCH не гарантированно; (в) важность: такие запросы можно безопасно повторить при таймауте или сетевой ошибке, а для POST нужен отдельный механизм (`Idempotency-Key`).
- **1.** Список верен, но нет объяснения про ретраи, или путает «идемпотентный» и «безопасный» (safe).
- **0.** Не знает определения или список в основном неверен.

### http.2 (apply) [Transferable: проектирование контракта]
**Вопрос:** Спроектируйте эндпоинт списка заказов текущего пользователя: фильтр по статусу, сортировка по дате (новые сверху), бесконечная лента на фронте. Опишите URL, query-параметры, формат ответа и ответы при ошибках.

**Рубрика:**
- **2.** Для 2 обязательно: (а) `GET` на коллекцию (`/orders?status=paid&limit=20&cursor=...` или `/me/orders`), пользователь берётся из токена, а не из параметра; (б) cursor/keyset-пагинация с обоснованием: стабильна при вставке новых записей и не деградирует, как `OFFSET`; в ответе `items` + `nextCursor` (или `null`); (в) `limit` с верхней границей; (г) ошибки: 400 с понятным телом (поле + причина, например Problem Details) при невалидных параметрах, 401 без токена; пустой список — это `200` с `[]`, а не `404`.
- **1.** Рабочий дизайн, но с offset-пагинацией без обсуждения trade-off или без контракта ошибок.
- **0.** Несогласованный дизайн (например, `POST /getOrders`, `404` на пустой список, `userId` в query без проверки).

### http.3 (design) [Transferable: надёжность при ретраях]
**Вопрос:** Клиент отправляет `POST /payments`, ловит таймаут и повторяет запрос. В итоге деньги списались дважды. Как спроектировать API и сервер, чтобы это не повторялось?

**Рубрика:**
- **2.** Для 2 обязательно: (а) `Idempotency-Key` генерируется клиентом на **операцию** (один и тот же при ретраях); (б) сервер сохраняет ключ с результатом (и хешем тела запроса), а на повтор возвращает сохранённый ответ, не выполняя операцию заново; (в) гонка двух одновременных запросов с одним ключом решается уникальным ограничением в БД или блокировкой: второй получает 409 либо ждёт; (г) TTL хранения ключей.
- **1.** Идея «проверять дубликаты» или «блокировать кнопку» без устойчивого серверного механизма, или ключ есть, но гонка не учтена.
- **0.** Нет решения.

## 4. `nest`: NestJS

### nest.1 (recall)
**Вопрос:** В каком порядке запрос проходит через middleware, guards, interceptors, pipes, контроллер и exception filters? Для чего нужен каждый слой?

**Рубрика:**
- **2.** Для 2 обязательно: (а) порядок: middleware → guards → interceptors (до) → pipes → handler → interceptors (после) → exception filters (при исключении); (б) guard решает, пускать ли запрос (авторизация, есть доступ к `ExecutionContext` и метаданным через `Reflector`); (в) pipe валидирует и трансформирует аргументы; (г) interceptor оборачивает выполнение: логирование, маппинг ответа, таймаут, кеш; (д) filter превращает исключение в HTTP-ответ.
- **1.** Назначение слоёв верно, но порядок ошибочен (например, pipes до guards), или наоборот.
- **0.** Не различает слои.

Please make sure that the argument PaymentsService at index [0] is available in the OrdersModule context.` Почему и как исправить? @Injectable()
export class OrdersService {

@Module({ providers: [OrdersService], controllers: [OrdersController] })

### nest.3 (design)
**Вопрос:** Нужно, чтобы во всех логах в рамках запроса был `requestId`, а сервисы глубоко в цепочке знали текущего пользователя. Коллега предлагает `UserContextService` со `scope: Scope.REQUEST`, внедряемый везде. Какие последствия? Какая альтернатива?

- **1.** Знает про стоимость создания на каждый запрос, но не про «всплывание», или предлагает явно передавать user во все методы без обсуждения ALS.
- **0.** Не видит проблем.

## 5. `pg`: PostgreSQL

### pg.1 (recall)
**Вопрос:** Расшифруйте ACID одним предложением на букву. Какой уровень изоляции в PostgreSQL по умолчанию и какие аномалии он допускает?

**Рубрика:**
- **2.** Для 2 обязательно: (а) верные A/C/I/D с краткими смыслами; (б) по умолчанию Read Committed; (в) он допускает неповторяемое чтение и фантомы, а в паттерне read-modify-write и потерянное обновление; (г) грязного чтения в PostgreSQL нет ни на каком уровне.
- **1.** ACID верно, но неверен уровень по умолчанию или аномалии.
- **0.** ACID не раскрыт.

### pg.2 (apply) [Transferable: рассуждение о доступе к данным]
**Вопрос:** Есть индекс и три запроса к таблице `orders` (миллионы строк, тысячи пользователей). Для каких запросов индекс поможет и как именно? Как вы это проверите?
```sql
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at);

-- A
SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;
-- B
SELECT * FROM orders WHERE created_at > now() - interval '1 day';
-- C
SELECT * FROM orders WHERE user_id = 42 AND status = 'paid';
```

**Рубрика:**
- **2.** Для 2 обязательно: (а) A: индекс используется полностью: поиск по `user_id` и уже упорядоченный `created_at` (обратный проход), отдельной сортировки нет, `LIMIT` останавливает чтение после 20 строк; (б) B: условие только на вторую колонку, правило левого префикса не выполняется, поэтому скорее всего Seq Scan, а нужен отдельный индекс на `created_at`; (в) C: индекс сужает по `user_id`, а `status` проверяется фильтром после чтения строк. Это нормально, если заказов у пользователя немного, иначе индекс `(user_id, status)` или частичный; (г) проверка через `EXPLAIN (ANALYZE, BUFFERS)` на реалистичном объёме данных с актуальной статистикой.
- **1.** A и B верно, но нет рассуждения про сортировку в A или про фильтр в C, либо нет способа проверки.
- **0.** Считает, что индекс помогает во всех трёх одинаково, или не знает правила левого префикса.
- **Бонус:** PG 18 умеет skip scan по составному B-tree, но для B это выгодно только при малом числе различных `user_id`; упоминает `Index Only Scan`/`INCLUDE`.

### pg.3 (debug) [Transferable: конкурентность]
**Вопрос:** Баланс 100. Два параллельных запроса списывают по 70, оба проходят, итоговый баланс 30. Почему? Поможет ли просто обернуть код в транзакцию? Предложите минимум два исправления.
```ts
const { balance } = await db.one('SELECT balance FROM accounts WHERE id = $1', [id]);
if (balance < amount) throw new InsufficientFunds();
await db.none('UPDATE accounts SET balance = $1 WHERE id = $2', [balance - amount, id]);
```

**Рубрика:**
- **2.** Для 2 обязательно: (а) это гонка read-modify-write (lost update): оба читают 100 до записи; (б) транзакция с уровнем по умолчанию (Read Committed) **не** спасает; (в) минимум два корректных способа: атомарный условный `UPDATE ... SET balance = balance - $1 WHERE id = $2 AND balance >= $1` с проверкой числа изменённых строк; `SELECT ... FOR UPDATE` внутри транзакции; Repeatable Read/Serializable с повтором при ошибке сериализации (40001); оптимистическая блокировка через колонку `version`; (г) `CHECK (balance >= 0)` как страховка.
- **1.** Видит гонку и даёт одно исправление, но уверен, что транзакция сама по себе помогает, или не знает про ретраи при Serializable.
- **0.** Не видит гонки.

## 6. `orm`: Prisma и доступ к данным

### orm.1 (recall)

## 7. `auth`: аутентификация и безопасность

### auth.1 (recall)
**Вопрос:** Как правильно хранить пароли пользователей? Почему не SHA-256, даже с солью?

**Рубрика:**
- **2.** Для 2 обязательно: (а) медленная адаптивная функция с солью: argon2id (рекомендация OWASP), bcrypt или scrypt; соль уникальна для каждого пользователя; (б) SHA-256 быстрый, поэтому перебор на GPU дешёвый, а медленные функции настраиваются по стоимости (work factor, память); (в) пароли никогда не шифруют обратимо.
- **1.** Называет bcrypt/argon2, но не объясняет, чем плох быстрый хеш.
- **0.** Предлагает MD5/SHA или шифрование.

### auth.2 (apply/design)
**Вопрос:** Спроектируйте схему access/refresh токенов для SPA на React и API на NestJS. Где на клиенте хранится каждый токен, сколько живёт, как работает обновление и logout?

**Рубрика:**
- **2.** Для 2 обязательно: (а) короткий access JWT (5–15 мин) хранится в памяти приложения и уходит в заголовке `Authorization`; (б) долгий refresh хранится в cookie `HttpOnly; Secure; SameSite` (по возможности с ограниченным `Path`), а на сервере лежит его хеш, чтобы можно было отозвать; (в) ротация: при каждом refresh выдаётся новый, старый инвалидируется, а повторное использование старого отзывает всю цепочку; (г) logout — отзыв refresh на сервере и очистка cookie; (д) почему не localStorage: токен доступен при XSS.
- **1.** Рабочая схема, но токены в localStorage без обсуждения XSS, либо нет отзыва и ротации.
- **0.** Один долгоживущий JWT без возможности отзыва.
- **Бонус:** защита refresh-эндпоинта от CSRF (SameSite, проверка `Origin`), единый «single-flight» refresh на клиенте при параллельных 401.

**Рубрика:**

## 13. `delivery`: Docker, CI, конфигурация, логи

### delivery.1 (recall)
**Вопрос:** Чем Docker image отличается от container? Что такое multi-stage build и зачем он нужен для NestJS-приложения?

**Рубрика:**
- **2.** Для 2 обязательно: (а) image — неизменяемый слоёный шаблон, container — запущенный экземпляр с собственным записываемым слоем; (б) multi-stage: на стадии сборки ставятся devDependencies и выполняются `tsc`/`prisma generate`, а на финальную стадию копируются только `dist` и production-зависимости; (в) выгода: образ меньше, меньше поверхность атаки, нет исходников и инструментов сборки; (г) порядок слоёв ради кеша: сначала копируется lockfile и ставятся зависимости, потом копируются исходники.

## 14. `sysdesign`: system design уровня Middle

### sysdesign.1 (recall/explain)
**Вопрос:** Что нужно, чтобы NestJS-API можно было запустить в 3 экземплярах за балансировщиком? Назовите, что сломается, если просто запустить три копии.

**Рубрика:**
- **2.** Для 2 обязательно: (а) приложение должно быть stateless; (б) минимум три конкретные проблемы: сессии или кеш в памяти процесса (нужен Redis/БД), загруженные файлы на локальном диске (нужно объектное хранилище), cron/фоновые задачи выполнятся трижды (нужна очередь или лидер), in-memory rate limit, websocket-подписки (нужен pub/sub-адаптер); (в) пул соединений: экземпляры × размер пула ≤ `max_connections` (иначе PgBouncer); миграции выполняются один раз, а не каждым экземпляром.
- **1.** Говорит «stateless», но называет меньше трёх конкретных проблем.
- **0.** Не видит проблем.

### sysdesign.2 (apply/design) [Transferable: декомпозиция долгих операций]
**Вопрос:** Спроектируйте «экспорт заказов в CSV»: до 1 млн строк, генерация до 5 минут. Как выглядит API, где выполняется работа, как пользователь узнаёт о готовности?

**Рубрика:**
- **2.** Для 2 обязательно: (а) асинхронная задача: `POST /exports` возвращает `202 Accepted` с `jobId`, HTTP-запрос не держится 5 минут; (б) очередь (например, BullMQ на Redis) и отдельный воркер; (в) статус через `GET /exports/:id` (polling) или SSE/WebSocket/уведомление; (г) генерация потоком: курсор или батчи из БД → CSV-stream → объектное хранилище → ссылка с ограниченным сроком (presigned URL), без сборки файла в памяти; (д) ретраи и таймаут задачи, ограничение числа одновременных экспортов на пользователя.
- **1.** Фоновая задача есть, но файл собирается в памяти, или нет механизма статуса, или работа идёт в процессе API без очереди.
- **0.** Синхронный эндпоинт.

### sysdesign.3 (design) [Transferable: согласованность при отказах]
**Вопрос:** После создания заказа нужно отправить письмо и событие в аналитику. Сейчас эти внешние HTTP-вызовы делаются **внутри** транзакции создания заказа. Какие тут проблемы и как это переделать?

**Рубрика:**
- **2.** Для 2 обязательно: (а) внешние вызовы удлиняют транзакцию, держат соединение и блокировки, а при медленном внешнем сервисе деградирует вся БД; (б) побочные эффекты не откатываются: письмо может уйти, а транзакция откатиться. И наоборот: коммит прошёл, а отправка упала (dual write); (в) решение — transactional outbox: в той же транзакции записывается строка в таблицу outbox, отдельный воркер или relay читает её и публикует в очередь или вызывает API с ретраями; (г) доставка at-least-once, поэтому обработчики должны быть идемпотентными (ключ события); бонус: backoff и DLQ.
- **1.** «Вынести после коммита» или «отправить в очередь» без учёта падения между коммитом и отправкой, или без идемпотентности.
- **0.** Не видит проблем.
